# Pibox

Pibox is a Pi extension that creates complete Pi RPC workers in Microsandbox or smolVM sandboxes. Sandbox configuration stays provider-native; Pibox owns only worker naming, bootstrap, RPC, authentication, and cleanup.

## Requirements

- Node.js 24 or newer
- one supported sandbox runtime:
  - Microsandbox 0.7.14 (installed with this package; Pibox selects its matching bundled runtime rather than a stale runtime in `~/.microsandbox`);
  - smolmachines 1.32.4 (installed with this package) plus `smolvm` CLI 1.34.1 or newer; live TCP publishing requires `net_backend = "virtio-net"`
- at least one model credential in the host Pi profile

```sh
npm install
npm run typecheck
npm run lint
```

## Quick start

Install dependencies, choose a provider example, and start Pi with the Pibox extension:

```sh
npm install
(cd examples/microsandbox && pi -e ../../src/index.ts --pibox)
```

`--pibox` reads `pibox.toml` from the current directory, creates the configured worker, and routes normal prompts and user bash commands to it. Remove the worker with `/pibox-rm`.

Alternatively, start Pi without creating a worker and use the commands interactively:

```sh
pi -e ./src/index.ts
```

```text
/pibox --config examples/microsandbox/pibox.toml
/pibox-rm <worker-name-shown-at-startup>
```

For repeated local use, `pi install .` loads the package without `-e`, so `pi --pibox` is sufficient. A Docker Compose example with TanStack Start, Quarkus, PostgreSQL, mise, and a bind-mounted Microsandbox workspace is available in [`examples/microsandbox/full-stack/`](examples/microsandbox/full-stack/).

## Configuration

Pibox loads `pibox.toml` from the current directory unless a command or tool supplies another path.

```toml
provider = "microsandbox"

[pibox]
name = "pibox-demo"
nameSuffix = "worktree"
workdir = "/workspace"

[sandbox]
image = "ghcr.io/manuschillerdev/pibox-base:bookworm"
network = { trustHostCAs = true }
ephemeral = true
replace = true
```

`provider` must be `microsandbox` or `smolvm`. `[pibox]` controls the worker name and guest working directory. `[sandbox]` uses the selected provider's native names, units, and structures. Microsandbox enables `network.trustHostCAs` by default so guests trust the host's configured roots; set `network = { trustHostCAs = false }` to opt out.

### Caches

Pibox can mount disposable package-manager caches and apply each tool's documented cache environment automatically:

```toml
[caches.pnpm]
scope = "repository"

[caches.maven]
scope = "user"

[caches.mise]
scope = "user"
```

`repository` is the default scope and is shared by Git worktrees through their common Git directory. `user` shares the cache between all Pibox workers owned by the current host user. A known preset's guest mount can be overridden without separately changing its environment:

```toml
[caches.pnpm]
mount = "/custom/pnpm-cache"
```

Built-in presets are `npm`, `pnpm`, `yarn`, `bun`, `pip`, `uv`, `poetry`, `maven`, `gradle`, `cargo`, `go`, `nuget`, `composer`, `bundler`, `deno`, and `mise`. Unknown cache names require an explicit absolute `mount` and do not generate environment variables.

Host data lives under `$TMPDIR/pibox-<uid>/caches/user/` or `$TMPDIR/pibox-<uid>/caches/repository/<repository-hash>/`. Cache data is disposable and may be removed by the host operating system. `[pibox.env]` may contain additional literal environment values; names generated by cache presets cannot be overridden there.

Pibox uses its Debian base image, which includes pinned Node.js, Pi, and agent-browser runtimes under `/opt/pibox`, Chromium with the agent-browser skill, mise, Docker Engine, its matching CLI, and Docker Compose. The browser skill is available inside worker profiles without copying host skills or downloading a browser. Docker uses the nested-VM-compatible `vfs` storage driver. Pibox starts Docker, runs `mise install` in the configured workdir, writes the guest extension and auth file through stdin, and starts Pi in RPC mode. See [`examples/`](examples/) for each provider.

## VS Code over SSH

Run `/pibox-vscode` for the connected worker, or `/pibox-vscode <worker>`, to prepare SSH and open its configured guest workdir in VS Code. Requires a macOS/Linux host with `code`, OpenSSH, Microsoft's **Remote - SSH** extension in the default VS Code profile, and a **smolVM** worker using the Pibox Debian image with virtio-net networking. Microsandbox publication is not supported. The separate [Pibox SSH extension for VS Code](extensions/vscode/README.md) remains available for manually configured endpoints and saved profiles; it is not required by the slash command.

After confirmation, the command installs `openssh-server` if missing (requires guest apt/network access), starts an isolated key-only **root** SSH daemon on a free guest port, publishes a host-loopback TCP endpoint, and opens VS Code. Root matches Pibox's existing worker identity without changing workspace ownership or permissions; the editor can access everything guest root can, including guest credentials and writable host mounts. Existing SSH daemons, `/etc/ssh` settings, and user authorized keys are not replaced. Automatic installation uses a temporary deny-service-start policy, or preserves the image's existing deny-all policy; other existing `policy-rc.d` policies require you to install OpenSSH yourself first.

Each live worker gets an unpassphrased Ed25519 identity stored only on the host and a host-key pin obtained through trusted provider exec, not network scanning. Password login and agent forwarding are disabled; host-key verification stays strict. Host files live under `~/.ssh/pibox-vscode/<instance>/` with private permissions. A one-time managed `Include` is prepended to `~/.ssh/config`, preserving its contents and saving `config.pibox-backup-*`; unsafe permissions, symlinks, locks, and conflicting effective SSH settings fail closed. Do not edit that file concurrently with setup. Use Remote - SSH's **default SSH config file**: custom `remote.SSH.configFile`/SSH binary overrides and non-default VS Code profiles are unsupported.

Repeating the command reuses its live identity, daemon, and publication. `/pibox-net` shows the raw TCP endpoint and can unpublish it; running `/pibox-vscode` republishes as needed. Keep the controller running. Stop/remove/reload/shutdown revokes owned publications and deletes the worker's host keys/config; the VM stop terminates SSH sessions. The harmless Include and config backups remain. Failed setup rolls back its daemon/publication where possible; installed packages remain. Cleanup failures stay retryable and retain host files until revocation succeeds. After a controller crash, stop/remove the VM before deleting stale instance directories; native mappings and existing TCP sessions may otherwise remain. Guest SSH requires a working root PAM account and VS Code Server prerequisites; unusual custom images may need manual setup.

A disposable, credential-free live SSH check (does not edit your SSH config or launch VS Code) is available with `node tests/smolvm-vscode-live.mjs`.

## Start and communicate

Start Pi with the configured worker already selected:

```sh
PI_CODING_AGENT_DIR="$HOME/.pi/profiles/pibox-controller" pi --pibox
```

Interactive commands:

- `/pibox` creates or enters the worker for the current worktree. Repeating it reconnects to that active worker without replacing its session.
- `/pibox-leave` disconnects and stops the routed worker.
- `/pibox-leave --keep-running` disconnects without stopping it.
- `/pibox-stop [worker]` stops an active worker.
- `/pibox-rm [worker]` stops and removes an active worker, or removes a worker stopped earlier in this controller.

On graceful Pi exit, reload, or session replacement, Pibox stops its workers; it does not suspend them or delete their disks. `/pibox-leave --keep-running` keeps a worker running only while its controller session remains alive. Abrupt termination (such as `kill -9`) cannot guarantee cleanup.

smolVM retains stopped machines and their names. A fresh controller reopens machines created with Pibox ownership/configuration labels when the requested configuration, mounts, credential bindings, and security policy match. Stopped machines start again; running machines are not restarted. An exclusive controller lock prevents concurrent Pibox sessions from sharing a guest. Crash-orphaned locks require ownership verification before recovery; the error identifies the lock file. If startup cannot confirm guest RPC closure, it retains the VM and lock rather than letting another controller take over. Legacy machines without these labels are left untouched and require explicit ownership/configuration verification before migration; automatic migration is not supported. Failed startup never deletes a reused machine. Within the original controller, use `/pibox-rm` after `/pibox-stop` only when intentionally discarding its data for a fresh worker.

The smolVM example does not mount the host worktree by default. `/workspace` and Docker volumes may contain guest-only data; stopping preserves that data, but removing the VM deletes it. Host mounts and disposable caches are separate from the guest root filesystem.

Model-facing tools retain their worker names: `worker_create`, `worker_prompt`, `worker_state`, `worker_steer`, `worker_abort`, `worker_set_model`, and `worker_remove`.

Interactive prompts use the host's selected model and thinking level. Provider-emitted thinking is shown while streaming and retained across tool turns above the final answer; `worker_prompt` also returns that prompt's thinking in `lastAssistantThinking`. A non-reasoning model or a provider that does not emit thinking cannot display it. Changes to host extension code require a fresh load; loading a local checkout with `--no-extensions -e ./src/index.ts` avoids loading an installed Pibox copy as well.

## Network overlay

`/pibox-net` lists guest TCP services in a compact dialog. Docker names default to `<compose-project>-<compose-service>`, or the container name. A short worker namespace prevents collisions; multiple ports/replicas get deterministic suffixes. Matching Docker IPv4/IPv6 wildcard bindings appear once.

- **Enter:** name and publish; **Tab:** HTTP or raw TCP.
- **U / Ctrl+U:** unpublish from list/form. **R:** refresh. **C:** copy endpoint. **O:** open browser. **Esc:** close/back.
- HTTP publication asks permission for exact guest hostname mappings. If the host needs a mapping, the same overlay shows the bounded `/etc/hosts` command and requests separate authorization. Cancellation publishes nothing new.

### One canonical HTTP URL

```text
http://<service>.<worker>.pibox.test

Host browser → loopback:80 → embedded Portless → native smolVM port → service
Guest → native smolVM host gateway:80 ───────────┘
```

Portless handles HTTP/WebSockets and exact in-memory routes. No TLS, certificates, trust installation, custom DNS server, guest relay, or Docker-client configuration is involved. Native virtio-net maps `host.smolvm.internal` to the host gateway, subject to smolVM egress policy. Worker namespaces are routing names, **not security boundaries** against other clients with host access. HTTP provides no encryption and may not satisfy browser secure-context features or applications that require HTTPS.

The proxy binds port **80** on both wildcard address families without elevation where supported (macOS); Portless rejects non-loopback peers before HTTP parsing and on requests/upgrades. There is no high-port fallback or automatic sharing with another controller. Linux requires low-port permissions configured separately. Pibox never elevates Pi or changes firewall rules, sysctl, or operator policy. Existing loopback listeners are checked before binding; an unrelated process binding a specific address later is an external race.

Host setup appends only the requested `.pibox.test` name to `/etc/hosts` as loopback. Correct unmanaged mappings are reused; conflicts fail closed. All unrelated entries, including Portless's shared block, remain untouched. Portless's native hosts writer replaces its entire shared block, so Pibox uses a narrow append-only helper instead. On macOS only that displayed helper requests administrator authorization; Linux uses `pkexec`. **Host entries remain after unpublish/shutdown** as durable name setup, but do not keep any route or forwarding active. Removing these optional entries later is a separate explicit administrator action.

Guest setup maps exact names to the native host gateway, preserving unrelated entries and other workers. Managed guest entries are removed on unpublish. Docker discovery supplies service names only; containers do not inherit the VM's `/etc/hosts`. Arbitrary container-client access is not configured. Host/guest HTTP status is displayed separately; HTTP 502 means upstream unavailable, while HTTP 401/403 remain authentication responses.

**Existing workers:** earlier Pibox versions injected `SMOLVM_PUBLISH_ADDR=127.0.0.1`, which smolVM interprets as fleet mode and blocks host gateway access. New workers no longer receive that injected setting. Explicit operator values remain untouched. An old worker may need an explicitly coordinated stop/start under the intended policy; Pibox never restarts it automatically. Preserve guest disks and Docker volumes—do not delete/recreate a VM containing data just to change networking.

**Application configuration:** use the displayed HTTP URL for public origins/OAuth callbacks/allowed hosts, e.g. Coder's `CODER_ACCESS_URL`. Pibox never guesses or rewrites app settings. Old publications do not silently migrate: unpublish/re-publish and update the app explicitly. `.localhost` cannot provide the same meaning inside a VM, which is why shared URLs use `.pibox.test`.

### Publication and cleanup

Publishing supports **smolVM 1.34.1+**, native TCP with virtio-net. Microsandbox publication remains deferred. Services must bind **`0.0.0.0` in the VM**; Docker services must publish an IPv4-wildcard port into the VM. Guest-loopback-only, IPv6-only, UDP and container-private ports are not published. Raw TCP needs no hostname setup and remains a numeric loopback endpoint. A non-loopback `SMOLVM_PUBLISH_ADDR` override is refused, not rewritten.

A small host-only dual-loopback bridge pins the IPv4 native destination so Portless cannot race into an unrelated IPv6 service. Do not edit the same VM's mappings concurrently outside Pibox. Native unpublish stops new connections but existing raw TCP connections may finish; HTTP unpublish closes proxy/bridge connections.

Owned routes, managed guest entries and native mappings are removed on unpublish or graceful cleanup. Failures remain visible and retryable. Pre-existing mappings remain untouched. After a controller crash native mappings and guest entries can remain: inspect and clean those explicitly. No cleanup after hard termination is guaranteed.

### Local network test

```sh
npm install
smolvm --version # 1.34.1 or newer
# Only if you accept model credentials inside the guest:
(cd examples/smolvm && PIBOX_SMOLVM_AUTH_POLICY=guest-environment pi --no-extensions -e ../../src/index.ts --pibox)
```

Start a guest server, then publish from the overlay:

```text
!nohup /opt/pibox/node/bin/node -e 'require("http").createServer((req,res)=>res.end("Hello from Pibox\n")).listen(3456,"0.0.0.0")' >/tmp/pibox-net-test.log 2>&1 </dev/null &
/pibox-net
```

Publish `3456` as `hello` using HTTP, review/approve the guest and any required host mapping, then open the displayed URL. Curl **the same URL** from the guest. Unpublish and verify it stops serving. Publication never restarts the VM.

Credential-free tests create/delete only uniquely named disposable VMs:

```sh
node tests/smolvm-network-live.mjs # native mapping lifecycle
node tests/smolvm-http-live.mjs    # same HTTP URL from host and guest; WebSocket; cleanup
```

The HTTP test overrides only the host lookup for its requests; it does **not** prove host OS resolution is configured. Guest checks use normal resolution. It needs internet access for Alpine packages and free host port 80. If another controller owns port 80, `PIBOX_TEST_HTTP_PORT=0 node tests/smolvm-http-live.mjs` explicitly exercises an ephemeral test port instead; production never falls back. It does not modify existing VMs, host `/etc/hosts`, trust, resolver configuration, or Coder.

## Authentication

Credential discovery remains in the worker layer. Provider adapters install credentials according to their native security model:

- **Microsandbox:** TLS secret substitution with live rotation.
- **smolVM:** blocked by default because the real token enters the guest process environment. To explicitly accept that weaker policy, set `PIBOX_SMOLVM_AUTH_POLICY=guest-environment`. Pibox then passes host environment references through `smolvm machine exec --secret-env`; it does not write the token to the guest auth file.

The local smolmachines SDK does not apply `MachineConfig.image` to the persistent guest rootfs. The smolVM adapter therefore uses the CLI with the opaque `[sandbox]` table serialized as a Smolfile, preserving a Debian image-backed machine for creation, lifecycle, and raw duplex execution. Existing-machine inspection and network publication use SDK `Machine.open()` without booting the machine. Startup uses CLI start only for a verified stopped machine; publication never restarts it. Neither path calls SDK create/connect. Do not add `-t`; Pi RPC requires unmodified pipes.

See [`docs/typescript-extension-auth-relay.md`](docs/typescript-extension-auth-relay.md) for the architecture and verification matrix.
